## Part 1 - Sandboxing technology for agents

### 1.1 What the major agents actually use

Claude Code (Anthropic) [PRIMARY: https://code.claude.com/docs/en/sandboxing ; https://github.com/anthropic-experimental/sandbox-runtime ; https://www.anthropic.com/engineering/claude-code-sandboxing (2025-10-20)]
- Built-in "sandboxed Bash tool" covers only shell commands (Bash/PowerShell/Monitor) and their children; Read/Edit/WebFetch, MCP servers and hooks run outside it. To put everything behind one boundary Anthropic says to run the whole process in `@anthropic-ai/sandbox-runtime` (srt), a container or a VM.
- macOS: Seatbelt (`sandbox-exec`) with dynamically generated profiles. Linux/WSL2: bubblewrap (user namespaces + bind mounts) + `socat`; network namespace is removed entirely and HTTP/SOCKS5 proxies listen on Unix sockets bind-mounted into the sandbox. Optional seccomp-BPF filters: (a) block creation of AF_UNIX sockets; (b) block user-namespace creation (`unshare`/`clone` with NS flags, `setns`, `mount`, `pivot_root`, `clone3`) so a sandboxed process cannot undo bind-mount protections. Native Windows: unsandboxed in Claude Code; srt has an alpha Windows mode that runs commands as a dedicated `srt-sandbox` local user with a write-restricted token, NTFS ACEs and a Windows Filtering Platform (WFP) egress fence keyed to that SID (loopback proxy ports 60080-60089). Known Windows gaps: Schannel-based clients (curl.exe, Invoke-WebRequest, .NET HttpClient, winget, cargo) cannot complete TLS inside; system-resolver DNS is not fenced; SMB/WSL traffic not fenced; token-switch bypasses.
- Network model: proxy decides by client-supplied hostname; by default does NOT terminate/inspect TLS. Experimental `network.tlsTerminate` makes the built-in proxy MITM TLS (mint leaf cert per SNI) so `mask` credential substitution can work. Docs explicitly warn: "Allowing broad domains such as github.com can create paths for data exfiltration ... code running inside the sandbox can potentially use domain fronting or similar techniques to reach hosts outside the allowlist." Proxy also refuses connections where an allowed name resolves to loopback/link-local (incl. 169.254.169.254)/own-interface addresses (DNS-rebinding guard).
- Known weakening switches to avoid: `enableWeakerNestedSandbox` (needed when bwrap cannot mount /proc inside an unprivileged container - "considerably weakens security"), `allowNestedUserNamespaces`, `allowUnixSockets` (e.g. docker.sock = host access), `allowAppleEvents` (removes code-execution isolation on macOS), `enableWeakerNetworkIsolation` (trustd exfil path). Ubuntu 24.04+ AppArmor blocks unprivileged userns by default (`kernel.apparmor_restrict_unprivileged_userns=1`) and needs a profile for bwrap.
- Other srt limitations (README): hard links let writes bypass deny paths; Linux deny-globs expanded at launch so later-created files aren't covered; seccomp blocks AF_UNIX *creation* only, not inherited/SCM_RIGHTS sockets; bwrap ~9000-argument limit.
- Claude Code also ships a reference devcontainer with `init-firewall.sh` (iptables/ipset default-deny, NET_ADMIN/NET_RAW) [PRIMARY: https://code.claude.com/docs/en/devcontainer]. The docs warn that with `--dangerously-skip-permissions` a dev container "does not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in ~/.claude".
- Anthropic's own ranking of isolation ("Choose a sandbox environment", [PRIMARY: https://code.claude.com/docs/en/sandbox-environments]): Bash sandbox < sandbox runtime < dev container / custom container < dedicated VM/microVM ("strongest separation"); cloud sessions run in Anthropic-managed isolated VMs with a network proxy enforcing a default allowlist and a separate GitHub proxy holding the token outside the sandbox. Anthropic reports an 84% reduction in permission prompts from sandboxing in internal use.

OpenAI Codex CLI [SNIPPET - developers.openai.com unreachable: https://developers.openai.com/codex/security ; https://openai.com/index/building-codex-windows-sandbox/ (2026-05-13) ; https://simonwillison.net/2025/Nov/9/codex-sandbox-investigation/]
- macOS: Seatbelt via `sandbox-exec -p <profile>` per `--sandbox` mode (read-only, workspace-write, danger-full-access). Linux: Landlock (filesystem) + seccomp (syscall-based network blocking); an experimental bubblewrap path (`-c features.use_linux_sandbox_bwrap=true`) [UNVERIFIED]. Official docs warn Landlock/seccomp may not work inside Docker if the host/container config lacks the APIs. Windows: experimental sandbox built on a restricted token derived from an AppContainer profile with capability SIDs for requested paths; network disabled by overriding proxy env vars and stubbing common network tools; OpenAI recommends WSL or Docker on Windows for real isolation. OpenAI evaluated AppContainer, Windows Sandbox and MIC labeling before building their own.

GitHub Copilot CLI / VS Code agent sandbox [SNIPPET: https://code.visualstudio.com/docs/agents/run/agent-sandboxing.md] - VS Code's agent sandbox supports domain-level network filtering on WSL2 but only all-or-nothing network on the native Windows terminal sandbox [UNVERIFIED].

Gemini CLI [KNOWLEDGE] - supports `--sandbox` using Docker/Podman containers or macOS Seatbelt profiles; not re-verified this session.

Hosted sandbox vendors
- E2B: Firecracker microVM per sandbox, own guest kernel, SOC 2 Type II [SNIPPET: https://e2b.dev/security]. One 2026 comparison claims "no outbound filtering"; E2B's own 2026 material says it supports allow/deny by IP/CIDR/domain - conflicting [UNVERIFIED].
- Modal: gVisor (user-space application kernel); no inbound by default, outbound restrictions supported; SOC 2 Type II; no microVM option [SNIPPET: modal.com resources].
- Daytona: Docker/OCI containers by default (shared host kernel) with optional Kata or Sysbox for stronger isolation; reportedly moved production code closed-source in June 2026 citing exploit-blueprint risk [SNIPPET/UNVERIFIED].
- Docker Sandboxes (`sbx`): launched 2026-01-30 (macOS/Windows first, Linux later); each agent session in a dedicated microVM with its own kernel and private Docker daemon (no host docker.sock); Docker wrote its own VMM on Apple Hypervisor.framework / Windows Hypervisor Platform / KVM rather than Firecracker (Linux-only); credentials "injected at runtime, outside the microVM boundary"; allow/deny network lists; free standalone, no Docker Desktop licence needed [PRIMARY: https://www.docker.com/blog/why-microvms-the-architecture-behind-docker-sandboxes/ (2026-04-16); https://www.docker.com/blog/docker-sandboxes-run-claude-code-and-other-coding-agents-unsupervised-but-safely/].
- Microsoft Execution Containers (MXC) SDK: early preview announced 2026-06-02 (Build 2026) for Windows + WSL; process isolation and session isolation now, micro-VM isolation on roadmap; Agent 365/Entra/Intune integration [SNIPPET: https://blogs.windows.com/windowsdeveloper/2026/06/02/windows-platform-security-for-ai-agents/].

### 1.2 Primitive-by-primitive notes

- Docker hardening baseline (all [KNOWLEDGE]/[SNIPPET]): rootless daemon (needs /etc/subuid,/etc/subgid; cgroups v2 required for rootless resource limits), `--userns-remap` or rootless so container root != host root, `--cap-drop ALL`, `--security-opt no-new-privileges`, `--security-opt seccomp=<profile>` (default profile blocks ~44 syscalls), `--read-only` + tmpfs, `--pids-limit`, memory/cpu cgroup limits, never mount docker.sock. `docker network create --internal`: "Restrict external access to the network" - no default route/NAT masquerade; containers still reach each other and the gateway, and the host can reach containers [PRIMARY-ish: docs.docker.com reference via snippet]. For agent egress, pair an `--internal` network with a proxy container that has a second, external network.
- gVisor (runsc): user-space kernel intercepting syscalls; platforms systrap (seccomp-based, default) or KVM; historically ~10-30% I/O overhead per vendors, a 2022 NAIST/IEEE study measured much worse on some workloads ("only 10% of default Docker performance") [SNIPPET]. gVisor assigns CVEs only to sandbox-boundary crossings.
- Firecracker: project figures <125 ms boot, <5 MiB overhead per microVM, 150 launches/s/host; Linux/KVM only (needs /dev/kvm - bare metal or nested virt) [SNIPPET].
- Kata Containers: OCI runtime launching a VM per pod via QEMU/Cloud Hypervisor/Firecracker/Dragonball; ~150-300 ms extra start, single-digit-MiB+ guest kernel memory [SNIPPET].
- bubblewrap: unprivileged user namespaces + mount namespaces; no syscall filtering itself (pairs with seccomp); shares the host kernel. Blocked on Ubuntu 24.04+ by AppArmor unless profiled.
- Landlock (Linux LSM, unprivileged): ABI 1 (5.13) filesystem; ABI 4 (6.7) TCP bind/connect restrictions; ABI 6 (6.12) IPC scoping (abstract Unix sockets, signals); ABI 7 (6.13/6.15 - sources conflict) audit logging of denials [SNIPPET: landlock.io, lwn.net]. Only restricts what it is told; needs seccomp for broader syscall control.
- macOS Seatbelt / `sandbox-exec`: man page says deprecated (since ~2016) but fully functional through macOS 15.x; Apple's own services, App Sandbox, Chromium, Bazel, Claude Code and Codex rely on it; profile language is undocumented and can change [SNIPPET]. Removal risk is real but no date announced.
- Windows: AppContainer (strong but designed for narrow apps; OpenAI judged it a poor fit for arbitrary dev tooling), Windows Sandbox (disposable Hyper-V VM, absent on Home SKU, slow cold start, works on a copy not your checkout), WSL2 (a Hyper-V utility VM running Linux; run Linux sandboxing inside it - this is both Anthropic's and OpenAI's recommendation), MXC SDK (preview).
- nsjail (Google, not official product): combines UTS/mount/PID/IPC/net/user/cgroup/time namespaces, cgroups v1/v2 limits, seccomp-bpf via Kafel policy language; battle-tested in Google CTF hosting [SNIPPET].

## Part 2 - Egress control and secret protection

### 2.1 Placeholder/sentinel credential proxies (secrets never enter the sandbox)

Anthropic's shipped designs (strongest reference implementation; [PRIMARY]):
- Claude Code local sandbox `credentials` setting: `{ "name": "GH_TOKEN", "mode": "mask", "injectHosts": ["api.github.com"] }` -> sandboxed commands see a per-session sentinel; the sandbox proxy substitutes the real value on outbound requests only to allowed hosts (must also be in `network.allowedDomains`); requires `network.tlsTerminate` because substitution happens inside request contents. Files can be masked too with an `extract` regex (Linux shows sentinel copy; macOS blocks the read). AWS SigV4: proxy detects the access-key sentinel and re-signs with real keys (needs both keys masked; presigned URLs/streaming uploads/SigV4A cannot be re-signed and are failed closed). `mode: "deny"` unsets env vars / blocks file reads instead. Masking is honored only from user/managed/CLI settings - never from repo-level settings - so a malicious repo cannot redirect secrets. [https://code.claude.com/docs/en/sandboxing#protect-credentials]
- Claude Code cloud sessions: "network secrets" stored on the environment; "Anthropic's agent proxy adds the key to requests for the hosts you list, after each request leaves the session's VM, so the key itself stays outside the VM"; GitHub traffic goes through a dedicated GitHub proxy; inside the VM `GH_TOKEN`/`GITHUB_TOKEN` read as the literal placeholder `proxy-injected`; the proxy checks repository scope (403 "GitHub access to ... is not enabled for this session"), rejects branch deletions and non-branch pushes (tags), and relies on GitHub branch protection for which branches may be updated. Signing keys also stay outside the sandbox. [https://code.claude.com/docs/en/cloud-environments ; https://code.claude.com/docs/en/security#cloud-execution-security]
- Docker Sandboxes: "Credentials are injected at runtime, outside the microVM boundary, and never baked into the environment." [PRIMARY docker.com]

Generic/open-source patterns [SNIPPET unless noted]:
- CyberArk Secretless Broker / Conjur sidecar injector: app connects to a local broker that authenticates to the target with vault-fetched creds; needs a protocol connector per target; maintenance status unclear [SNIPPET: developer.cyberark.com, conjur.org/secretless].
- HashiCorp Vault Agent (templating/injector sidecar writes short-lived dynamic creds to a file), 1Password Connect / Service Accounts (vault-scoped token, no per-request ephemeral creds), Doppler (service token, hosted only), Infisical (machine identities, dynamic secrets, k8s operator, OSS) [SNIPPET: bytebase.com, techplained.com comparisons]. None of these alone solves "agent must not see the secret"; they are the *source of truth* behind an egress-injection proxy.
- Agent-specific egress credential proxies: iron-proxy (Hermes Agent; terminates TLS, swaps opaque proxy token for real key), keycardai/egress-proxy (iptables redirect of all TCP to a sidecar, placeholder -> bearer swap, default-deny), agentcage (random decoy tokens, opaque CONNECT - so cannot inject into TLS), sandbase-harness PR #834 (placeholder substitution at egress), PromptLatch and KeyClaw (local MITM proxies that redact secrets *out* of LLM traffic and restore placeholders in responses) [SNIPPET: hermes-agent.nousresearch.com, github.com/keycardai/egress-proxy, github.com/lucamartinetti/agentcage].
- Design requirements distilled: (1) the only path out of the sandbox is the proxy (netns removal + Unix-socket bridge, or iptables REDIRECT in-container); (2) proxy must terminate TLS to rewrite request bodies/headers (so a harness CA must be trusted inside the sandbox and the proxy must re-verify upstream TLS); (3) per-secret host binding (`injectHosts`) so a GitHub token cannot be sent to attacker.com; (4) signed-request protocols (AWS SigV4, GCP, OCI) need re-signing not substitution; (5) config that authorizes injection must come from trusted scope, never the repo; (6) the LLM API key itself should also be proxy-injected: the agent calls the harness LLM proxy with a per-run virtual key, and the harness holds provider keys/OAuth tokens (LiteLLM-style virtual keys with RPM/TPM budgets, LangSmith LLM Gateway, Portkey [SNIPPET]). Claude Code's docs confirm `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`/`apiKeyHelper` route through a gateway and that the gateway's credential replaces the subscription login for billing [PRIMARY https://code.claude.com/docs/en/llm-gateway].

### 2.2 DNS/HTTP egress allowlists

- Squid: `ssl_bump peek` at step 1 to read SNI, `splice` allowlisted `ssl::server_name`, `terminate` the rest; `dstdomain` ACL for plain HTTP; without SNI (or with ECH) default-deny [SNIPPET: xebia.com/blog/how-to-configure-squid-as-an-egress-gateway]. Allows hostname allowlisting without MITM.
- Envoy: used by Lyft as an internet egress gateway mapping each service to allowed upstream hosts; Istio's SNI-based dynamic forward proxy pattern; Envoy Gateway IP/host restrictions [SNIPPET: eng.lyft.com; istio.io egress-sni]. Caveat (DeepInspect): "A permitted domain is still a live exfiltration channel" - inspecting payloads requires TLS termination.
- Tailscale: identity-based ACLs/grants; "Aperture" gateway (2026-08-06 blog) holds LLM/MCP/data credentials outside the agent harness and uses device-posture to restrict sandboxes that have open egress [SNIPPET: tailscale.com/blog/aperture-lethal-trifecta]. Useful when the harness must reach private services without exposing them to the sandbox.
- Anthropic devcontainer `init-firewall.sh`: iptables + ipset default-deny with resolved IPs of allowed domains (GitHub meta API ranges, npm, Anthropic API) [PRIMARY docs; script content not fetched].
- Claude Code cloud "Trusted" level = allowlisted registries/GitHub/cloud SDK domains only; "Custom" = your list; even with network "None" Claude Code can still reach the Anthropic API, "which may allow data to exit the VM" [PRIMARY].
- Anthropic sandbox proxy resolves allowed hostnames and refuses loopback/link-local/metadata/own-IP results (DNS-rebinding guard) - replicate this.

### 2.3 Detecting secret exfiltration

- Canary/honeytokens: Thinkst Canarytokens (hosted canarytokens.org or self-hosted) - AWS key tokens alert on any use (even sts:GetCallerIdentity) with source IP/user agent; recommended plants for agent sandboxes: fake `~/.aws/credentials`, fake `.env`/`.npmrc` tokens, decoy MCP server entries in agent config, canary URLs in CLAUDE.md/README [SNIPPET: zeltser.com, blog.thinkst.com]. Cheap, high-signal detection of "the agent read and used a secret it should not have".
- GitHub secret scanning push protection: blocks pushes containing supported secret patterns; default lets any writer bypass with a reason; "delegated bypass" routes bypass requests to a reviewer group, requests expire after 7 days, every bypass is an alert + audit-log event [SNIPPET: docs.github.com delegated-bypass]. The harness should run its own pre-push scan so the agent never trips server-side blocks.
- gitleaks: fast regex (~150 rules), MIT, pre-commit/sub-second, SARIF; no verification. TruffleHog: ~800 typed detectors with live credential verification, AGPL-3.0, scans git/S3/Docker/Slack; common practice is gitleaks pre-commit + TruffleHog in CI [SNIPPET: jit.io, appsecsanta.com]. Recommend: gitleaks on every agent commit/diff inside the harness before push; TruffleHog --only-verified on the final PR.
- Exfiltration channels to model: DNS (data in subdomain labels of attacker domain - mitigate by forcing all DNS through the harness resolver or disabling raw DNS from sandbox; Claude's bwrap design removes the netns entirely so there is no DNS path); HTTP CONNECT tunnels (opaque unless TLS-terminated; limit CONNECT to allowlisted SNI/port 443); domain fronting through broad allowlisted CDNs (explicitly warned by Anthropic); encoding data into allowed destinations (git push to attacker fork, issue comments, package publish, Hugging Face uploads - cf. Claude Code GHSA-fg94-h982-f3mm "Out-of-Band Data Exfiltration via Pre-Approved HuggingFace Domain in WebFetch", 2026-06-13 [PRIMARY listing]); image-URL rendering/markdown link exfil in chat UIs (EchoLeak/CamoLeak class); LLM-provider itself as a channel (the API is always reachable). Detection: entropy/length anomalies in DNS names, request-size and destination-cardinality baselines per run, canary tokens.

### 2.4 TLS interception tradeoffs

- Durumeric et al., "The Security Impact of HTTPS Interception" (NDSS 2017): nearly all middleboxes/AV interceptors reduced connection security and many introduced severe vulnerabilities; interception detectable by server via UA/handshake mismatch; breaks HPKP/pinning [SNIPPET: ndss-symposium.org].
- For an agent harness the calculus differs: the "client" is untrusted code you own the environment for, so MITM is the only way to (a) inject placeholders into request bodies, (b) filter paths/methods (e.g. allow `POST /repos/x/y/pulls` but not `DELETE`), (c) log for audit. Costs: must install harness CA into every trust store in the image (system, Node, Python certifi, Java cacerts, Go, Rust/rustls...); tools with pinning or Schannel (Windows) break; the proxy becomes a high-value target holding all secrets; upstream verification must be strict; memory/latency overhead (srt caps 256 tunnels, 1 MiB per-client buffer). Anthropic's default is *no* TLS termination (hostname-only allowlist) with opt-in `tlsTerminate`; mirror that: hostname/SNI allowlist by default, TLS termination only for hosts where injection or content policy is needed, opaque CONNECT refused elsewhere (`refuseOpaqueTunnels`).

### 3.3 Defenses with evidence

- OS-enforced sandboxing + default-deny egress (Parts 1-2) - the only controls that hold when the model is fooled. Anthropic: auto-mode classifier "is a per-action control, not an isolation boundary"; `bypassPermissions` "offers no protection against prompt injection" [PRIMARY permission-modes].
- Tool/capability allowlists and least-agency: repo-scoped, short-lived tokens (Docker's post-mortem of the GitHub-MCP exploit credits repository-scoped OAuth); per-run virtual LLM keys; MCP server allowlists (Claude Code managed MCP config); read-only by default; separate identities per agent (OWASP ASI03).
- Human-in-the-loop for side effects: GitHub MCP exploit "can be avoided if developers are careful to check and approve agent actions" but researchers note users choose "always allow". Trajectory Labs test cited by Willison: humans refused only 13.6% of swapped dangerous commands vs 89% blocked by Anthropic's auto-mode classifier [SNIPPET/UNVERIFIED]. Conclusion: approval prompts are weak against fatigue; gate *classes* of side effects (push, publish, deploy, delete, outbound non-allowlisted network) with explicit, rare, well-explained approvals rather than per-command prompts.
- Classifier/second-model review: Anthropic auto mode strips tool results from the classifier's input "so hostile content in a file or web page can't manipulate the classifier directly", runs a server-side probe on incoming tool results, pauses after 3 consecutive/20 total blocks, and drops broad allow rules on entry [PRIMARY permission-modes]. Anthropic made auto mode default for Pro/Max/Team from 2026-08-14; Anthropic staff claim near-complete mitigation but Willison and Rehberger dispute (Rehberger claims an 80%-success attack) [SNIPPET/UNVERIFIED].
- Content isolation of untrusted text: Claude Code WebFetch returns a separate model call's summary instead of raw page; "Avoid piping untrusted content directly to Claude"; wrap tool results as data with provenance tags; strip/normalize invisible Unicode (zero-width, bidi, tag characters) and flag hidden HTML comments before content reaches the model (Pillar/Knostic recommendation).
- Dual-LLM pattern (Willison) and CaMeL (Google DeepMind, "Defeating Prompt Injections by Design", arXiv 2503.18813): privileged LLM plans from the trusted user request only; quarantined LLM parses untrusted data without tool access; a custom interpreter tracks capabilities/provenance (taint) on every value and enforces policies before tool calls; solves 67-77% of AgentDojo tasks with provable security; cost = developers must write policies and users get confirmation prompts [SNIPPET: simonw.substack; css.csail.mit.edu camel.pdf]. For a coding harness the practical translation: the planner never reads raw web/issue content; a "reader" model produces structured, schema-validated extracts; any value derived from untrusted content is tainted and cannot flow into shell arguments, URLs, or git remotes without policy approval.
- Taint tracking / provenance at the harness level: record for each tool call which untrusted sources were in context; refuse side-effecting tools when tainted values appear in their arguments (Claude Code's per-command "allowed domains" also route to the classifier even with an allow rule).
- Supply-chain controls: verify packages exist and have history/downloads before install (slopsquatting guard), lockfile integrity gates (`npm ci`, hash-pinned lockfiles, diff review of lockfile URL/integrity changes), block `npm publish`/registry writes from sandbox, pin plugins/skills by commit SHA (and verify the pin, cf. GHSA-pq7j-f95f-qfcv), PATH hygiene (absolute tool paths, no repo-dir in PATH).
- Trust-on-first-use: do not load repo hooks, settings, MCP servers, or run any repo code before an explicit trust decision (lesson from CVE-2025-59536 and CVE-2026-21852).

### 5.2 Provenance, signing and evidence anchors
- SLSA (v1.0/v1.1, slsa.dev): Build track L1 = provenance exists; L2 = hosted build platform signs provenance; L3 = hardened build platform, provenance non-forgeable, isolated builds; v1.1 adds the Source track (L1-L3: version control, strong authentication / two-person review / verified history) [KNOWLEDGE; spec pages 404 at guessed GitHub paths]. For a harness: emit SLSA-style provenance (in-toto statement) for every agent-produced change: who/what agent, model + version, prompt hash, tool-call log hash, sandbox config hash, tests run and results.
- Sigstore gitsign [PRIMARY github.com/sigstore/gitsign]: keyless commit signing bound to an OIDC identity; Fulcio short-lived cert (~10 min on the public instance); signature (CMS/PKCS7) recorded in the Rekor transparency log ("hashed-rekord" of commit SHA + cert) or offline mode storing Rekor attributes in the commit; `gitsign verify` with `--certificate-identity`/`--certificate-oidc-issuer` is required because `git verify-commit` "only checks cryptographic integrity and Rekor existence"; supports RFC 3161 timestamps via `timestampServerURL`/`timestampCertChain`; GitHub does NOT show "Verified" for gitsign signatures (Sigstore root not in GitHub's trust root; ephemeral certs fail plain X.509 validation). GPG/SSH-signed commits do get GitHub's badge but need long-lived key management. Recommendation: the harness signs commits with its own identity (SSH or GPG key per harness instance for the GitHub badge) AND records a Sigstore/Rekor entry or an RFC 3161 timestamp over the provenance bundle for independent evidence; never give the sandboxed agent the signing key (Anthropic keeps "git credentials and signing keys" outside the sandbox).
- RFC 3161 Time-Stamp Protocol [KNOWLEDGE]: a TSA signs (hash, time) producing a TimeStampToken; free public TSAs include Sigstore's timestamp authority (timestamp.sigstore.dev), DigiCert, FreeTSA; use to prove a change/provenance existed before a given time independent of the harness's own clock. Rekor provides an append-only, Merkle-tree transparency log (CT-style) with inclusion proofs - good "evidence anchor" for audit; self-host Rekor for private data.

### 5.3 EU AI Act (Regulation (EU) 2024/1689) [SNIPPET: Gibson Dunn, Sidley, CSA note]
- Entered into force 2024-08-01; prohibitions and AI-literacy duties from 2025-02-02; GPAI model obligations from 2025-08-02 (apply to model providers - Anthropic/OpenAI/Google - not to a harness that only deploys them); governance/penalties 2025-08-02.
- Digital Omnibus on AI: provisional agreement reported 2026-06-22; CSA note says published in OJ 2026-07-24 as Regulation (EU) 2026/1744, in force 2026-07-27 [single-source, UNVERIFIED]. Effect: Annex III stand-alone high-risk obligations move from 2026-08-02 to 2027-12-02; Annex I product-embedded high-risk to 2028-08-02; Article 50 transparency obligations largely stay on 2026-08-02 with a watermarking/transparency extension to 2026-12-02 for systems already on the market; a new prohibition on non-consensual intimate imagery/CSAM generation from 2026-12-02.
- Relevance: a coding-agent harness is not itself high-risk unless used in an Annex III context (e.g., employment decisions); Article 50 transparency (inform users they interact with AI; mark AI-generated content) applies to deployers/providers of such systems - label agent-generated commits/PRs as AI-generated (already a GitHub/Claude practice: PR replies "labeled as coming from Claude Code"). Keep logs and human oversight features to support customers' own obligations.

### 5.4 EU Cyber Resilience Act (Regulation (EU) 2024/2847) [SNIPPET: docker.com CRA overview; goodwinlaw; noze.it]
- In force 2024-12-10/11. Article 14 reporting obligations apply from 2026-09-11 (24h early warning, 72h notification, final report 14 days after corrective measure for actively exploited vulnerabilities; 1 month for severe incidents) via ENISA single reporting platform. Full application 2027-12-11 (essential requirements, SBOM, security-by-default, vulnerability handling, CE marking).
