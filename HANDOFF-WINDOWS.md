## 1. Подготовка на Windows
Препоръчаният път е WSL2. Директно в PowerShell е проверен само `pnpm build` и част от `pnpm local`; пясъчникът и Docker
тестовете там не са проверявани (D-392).

В PowerShell като администратор:
```powershell
wsl --install -d Ubuntu
```
След това инсталирай Docker Desktop и включи: Settings → General → WSL 2 based engine и Settings → Resources → WSL integration →
Ubuntu. Дай му поне 4 CPU и 8 GB памет, за да е като машината, на която минаха тестовете.

Всичко останало е в терминала на Ubuntu. Клонирай в `~/`, не под `/mnt/c`, защото там правата и следенето на файлове не са
надеждни (D-094).
```bash
sudo apt update && sudo apt install -y git build-essential
curl -fsSL https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash
source ~/.bashrc
git clone https://github.com/SimoSabev/AI-Harness-NOIT.git ~/AI-Harness-NOIT
cd ~/AI-Harness-NOIT
git checkout phase/e9d-research
nvm install
npm i -g pnpm@12.14.0
pnpm install --frozen-lockfile
pnpm build
pnpm mandat images build
pnpm mandat fixtures build
pnpm mandat doctor
pnpm local
```
Страницата е на http://localhost:3000. `nvm install` чете версията от `.nvmrc` (24.22.0). Ако `pnpm mandat doctor` покаже
проблем, първо него оправи. Изискванията са и в `README.md`, раздел „Бърз старт по ОС“.

Клонът вече съществува на този компютър, ако си го дръпвал преди:
```bash
cd ~/AI-Harness-NOIT && git fetch origin && git checkout phase/e9d-research && git pull
```

### Какво не идва с git
- **Ключове:** Gemini и Exa се въвеждат отново на http://localhost:3000/keys. Сесията не ги чете и не ги пипа. Без `.env`.
- **Локални данни:** задачите, историята и настройките от Mac-а са в `.mandat` и в контейнера `mandat-local-db`. На новата машина
  започваш с празна база.
- **Образи:** строят се от `pnpm mandat images build`; никога не се публикуват.

## 3. Какво НЕ е готово
**Няма „CHECK OK“.** Последната пълна проверка беше преди комит 74df158:
- **Docker тестове:** 65 минаха, 1 падна, 1 пропуснат. Падна `conflict-wait.docker.test.ts`. Причината: втората задача намира
  поправката вече в main, фалшивият агент се сриваше с код 3, а новата логика правилно брои това за провал. 74df158 поправя
  фалшивия агент, без да пипа очакването на теста. Docker тестът още не е пускан след това.
- **`pnpm check`:** 1751 минаха, 12 паднаха с изтекъл лимит от 20 s (`daemon.test.ts`, `ledger.test.ts`, `board-column.test.ts`,
  `channels-role.test.ts`, `demo-offline-no-egress.test.ts`). Сами петте файла минават, 70 от 70. Вероятна причина: натоварване
  веднага след Docker тестовете. Това не е доказано.

Не е проверено на живо:
- истинска задача с Gemini, в която се вижда съобщение от доставчика;
- отговор на „hi“ без промяна (само unit тестове);
- българските текстове на живото състояние (видени са само английските);
- нищо от това на Windows.

Известни граници: агент, който каже „готово“ без промяна, се затваря с „няма променени файлове“; нов опит ползва същия модел;
`tasks.usd` се презаписва при всеки опит; броят от 10 опита на Gemini CLI е [НП]; суровият текст на грешката от Gemini остава в
свития лог.

## 4. Следващи стъпки
1. Настройка по раздел 1, с `pnpm local` спрян за тестовете.
2. Пълни тестове, първо Docker, после проверката, с пауза между тях:
   ```bash
   pnpm mandat images build
   pnpm test:docker
   pnpm check
   ```
   Docker тестовете отнеха около 70 минути на Mac с 4 CPU и 8 GB. Компютърът не бива да заспива. Търси буквално `CHECK OK`.
3. Паднал тест се разследва; очакванията му не се отслабват. Ако 12-те паднат пак, причината не е само натоварване.
4. Истинска задача с Gemini и „hi“ от страницата; ключът го въвежда човекът.
5. След „CHECK OK“ и след моето „да“: работа по `docs/tasks/e10a.md`, от фаза 0. Планът още не е започнат.

Разлики между Mac и WSL: `caffeinate` няма; бележките за Colima не важат; всички пътища са под `~/`.
